# Эскизно: единый профессиональный редактор и учебное пространство

**Дата:** 2026-11-10  
**Статус:** проект технического дизайна на утверждение; реализация не начата  
**Выбранный подход:** A — один движок рисования, два отдельных рабочих пространства.

## 1. Замысел и подтверждённые решения

«Эскизно» остаётся школой цифрового рисования для взрослых, но свободная студия развивается в полноценный редактор цифровой иллюстрации.

Подтверждено пользователем:

1. От обучения не отказываемся.
2. В обучении инструменты открываются постепенно и **навсегда** остаются доступными в последующих уроках; отдельный урок может временно ограничивать инструменты ради упражнения.
3. В свободном профессиональном редакторе **все реализованные инструменты доступны сразу**, независимо от учебного прогресса.
4. Движок рисования общий, интерфейсы обучения и свободной студии — разные (архитектурный вариант A).
5. Работы можно продолжать между режимами без потери рисовальных данных.

Продуктовый фокус: создание самостоятельных цифровых рисунков и иллюстраций. **Не обещаем на первом этапе совместимости и паритета с Photoshop, Krita и Procreate.**

## 2. Текущее положение (фактическая проверка кода)

Проверены файлы актуальной ветки `feat/e1-7-finish` (Draft PR #14):

- `apps/web/src/App.tsx`: навигация `Обучение` / `Свободная студия` / `Мои работы`. «Обучение» сейчас — вводная страница без рабочего процесса урока.
- `apps/web/src/studio/Studio.tsx`: создание обычного холста и проектов с референсом, управление панелью референса и подключение `EditorCanvas`.
- `apps/web/src/editor/EditorCanvas.tsx`: управление инструментами, жестами и UI в одном крупном компоненте; типы инструментов (`ink`, `erase`, `fill`, `shape`, `eyedropper`) определены здесь локально.
- `apps/web/src/editor/model.ts`: версия формата документа `2`, `DrawingProject` со слоями, кистями и опциональным `LessonContext`; `Stroke.points` содержит координаты без давления/наклона. Ограничение `MAX_LAYERS = 16`.
- IndexedDB и PNG реализованы; текущий импорт референсов и зум просмотра относятся к Draft PR #14.
- По состоянию на E1 browser gate #38 прошли TypeScript, unit и Chromium E2E; **испытания физического стилуса, планшета и телефона не завершены**.

Из этих фактов следует: имеющуюся модель и рендер следует **эволюционировать через совместимые изменения**, но не объявлять текущий Canvas2D-движок профессиональным без аудита производительности, точности пера и формата проектов.

## 3. Цели и явные ограничения

### Цели

- Один документ и один набор реализованных возможностей, работающие в обоих режимах.
- Учебный режим фокусирует ученика на нужном инструменте; свободный режим не зависит от прогресса.
- Неразрушающее редактирование там, где это возможно: слои, трансформации, маски, история.
- Предсказуемая работа мышью, касанием, клавиатурой и стилусом; приоритет планшета.
- Восстановление проектов, безопасное автосохранение и независимый экспорт.
- Доступность интерфейса и настраиваемые панели без потери холста на узком экране.

### Не цели первых этапов

- Клон всех возможностей Photoshop/Krita/Procreate.
- Сервер, обязательный аккаунт, облачная синхронизация, платежи и маркетплейс кистей.
- Обещание автоматической объективной оценки художественного качества.
- Немедленный PSD/AI/SVG round-trip, CMYK/prepress, монтаж видео или анимация.
- Переписывание v0.4 и всех E1-функций одним большим изменением.

## 4. Выбор архитектуры

| Подход | Суть | Оценка |
| --- | --- | --- |
| **A — выбран** | Общий Editor Core, самостоятельные `Learning Workspace` и `Professional Workspace` | Общее поведение документов и инструментов без дублирования интерфейсов |
| B — отвергнут | Один экран с переключателем ограниченного/полного набора | Быстрее старт, но учебный UX и профессиональные панели начинают конфликтовать |
| C — отвергнут | Два приложения с общими низкоуровневыми пакетами | Избыточная поддержка и риск расхождения версий для текущей команды |

**Логические границы (предлагаемые, не существующие папки):**

1. **Editor Core:** сериализуемая модель документа, команды и история, рендер и кеши, ввод/геометрия, ресурсы; без сведений об уроках и о том, какая панель открыта.
2. **Tool Registry:** стабильные ID инструментов и возможностей, метаданные UI, параметры, проверки применимости. Реестр объявляет только действительно реализованные инструменты.
3. **Tool Access Policy:** чистая функция, определяющая доступность инструмента в контексте режима и урока. Эта политика проверяется в UI и перед инициированием команды; скрытие кнопки само по себе не является ограничением.
4. **Professional Workspace:** полный набор реализованных инструментов, панели, история, настройки ввода, файлы, горячие клавиши.
5. **Learning Workspace:** цель и этап урока, подсказки, рамки упражнения, переход к следующему шагу, те же команды Editor Core.
6. **Learning Progress:** завершённые уроки, навсегда открытые инструменты, текущая позиция; локально и **отдельно от данных рисунка**.
7. **Project Storage:** единый путь автосохранения и миграций; любая работа открывается через Editor Core.

### 4.1 Политика доступа к инструментам

**Предлагаемый контракт, не готовое API:**

```ts
type WorkspaceMode = 'professional' | 'learning';
type ToolId = string; // стабильный идентификатор из реестра

interface ToolAvailabilityContext {
  mode: WorkspaceMode;
  implementedToolIds: ReadonlySet<ToolId>;
  permanentlyUnlockedToolIds: ReadonlySet<ToolId>;
  lessonIntroducedToolIds?: ReadonlySet<ToolId>;
  lessonAllowedToolIds?: ReadonlySet<ToolId>;
}
```

- **Professional:** все ID из `implementedToolIds`, без проверки прогресса. Нереализованные пункты не изображать рабочими.
- **Learning:** `(permanentlyUnlocked ∪ introducedInCurrentLesson) ∩ implemented`, затем, если есть ограничение урока, пересечение с `lessonAllowedToolIds`.
- Отключённый инструмент в обучении имеет понятное объяснение; просмотр чужого проекта не удаляет операции, созданные этим инструментом.
- Undo/Redo, навигация, восстановление и безопасное сохранение не должны блокироваться учебным ограничением.
- При смене урока некорректный текущий инструмент переключается на доступный без изменения рисунка.

### 4.2 Прогресс и разблокировка

- У каждого урока стабильный ID, версия содержания, список вводимых возможностей и проверяемый сигнал завершения.
- Завершение урока фиксирует событие прогресса и добавляет открытые возможности в `LearningProgress` **монотонно**: уже открытое не закрывается при изменении порядка уроков.
- Ограничение текущего урока не отнимает постоянную разблокировку, а лишь меняет набор инструментов этого конкретного упражнения.
- Переход между уроками и перезапуск браузера сохраняют прогресс локально.
- Не путать «прошёл урок» с «художественно освоил»: не выдавать автоматическую оценку, пока нет проверяемых критериев.
- Для первого вертикального среза годится детерминированная проверка действия (например, добавлен штрих нужным инструментом) и явное завершение шага. Субъективная оценка рисунка не входит в gate.
- При изменении схемы учебной программы старые записи прогресса мигрируются; неизвестные ID логируются безопасно и не дают доступа к несуществующим инструментам.

### 4.3 Проекты между режимами

- Рисунок всегда остаётся одним `DrawingProject`, независимым от внешнего интерфейса. Опциональный `LessonContext` хранит происхождение урока, а не доступность инструментов.
- **Предлагаемое UX-решение:** действие «Продолжить в свободном редакторе» создаёт именованную редактируемую копию с теми же слоями/вложениями; исходная учебная попытка остаётся доступной. Никаких незаметных перезаписей.
- Обратное открытие свободной работы в уроке не удаляет профессиональные слои или параметры; учебный режим может отобразить их без права редактирования ограниченным инструментом.
- Совместимость данных двусторонняя, но выполнение учебных критериев определяется действиями **в уроке**, а не фактом наличия сложного рисунка.
- Добавление новых типов операций требует `DOCUMENT_SCHEMA_VERSION`-миграций и тестов восстановления старых проектов; экспорт PNG не заменяет переносимого редактируемого формата.

## 5. Профессиональный редактор: границы функциональности

Порядок предложен по зависимостям, а не по визуальной эффектности.

| Очерёдность | Система | Минимальный полезный результат |
| --- | --- | --- |
| **P0 — фундамент** | Измерения производительности и памяти; стресс-тесты больших документов; реальный стилус; модель команд и совместимое сохранение | Выбраны допустимые размеры, пределы слоёв и бюджет отклика на основании измерений |
| **P1 — разделение режимов** | Реестр возможностей, policy, два UI, локальный учебный прогресс, один демонстрационный урок | «Профессиональный» всегда с полным набором, «Обучение» открывает инструмент навсегда |
| **P2 — редактирование** | Выделение, свободное перемещение и трансформация содержимого, группы слоёв, надёжные Undo/Redo | Объекты и области можно изменять без перерисовки с нуля |
| **P3 — качество рисунка** | Динамика кисти по нажиму/наклону, стабилизация, настраиваемые кисти, маски и режимы наложения | Стилус даёт контролируемую выразительную линию, операции остаются редактируемыми |
| **P4 — рабочий процесс** | Настраиваемые панели, клавиатурные команды, направляющие, симметрия, переносимый родной файл проекта | Можно выполнять полноценные иллюстрации и переносить редактируемые проекты |
| **P5 — расширения** | Дополнительные форматы, цветовые профили, оптимизация сложных фильтров и др. по реальному спросу | Расширение без обязательства поддерживать всё на старте |

**Не выбирать WebGL/WebGPU/OffscreenCanvas заранее только по моде.** Сначала инструментируем нынешний Canvas2D-рендер, сохранение и историю, измеряем на поддерживаемых устройствах, затем фиксируем необходимость более крупного движкового изменения. `Stroke.points` сейчас не содержит pressure/tilt; их добавление должно быть явным изменением схемы, а не скрытым полем UI.

## 6. Интерфейс: две оболочки

### Профессиональный режим

- Холст — визуальный центр. Группы инструментов, свойства кисти/цвета/слоя и референс работают как перестраиваемые панели.
- На широком экране допускаются закреплённые панели; на планшете — компактные сворачиваемые, на телефоне — поочерёдные панели без горизонтального переполнения.
- Состояние расположения панелей локальное и не должно менять содержимое DrawingProject.
- Клавиатурные команды и сенсорные элементы имеют одинаковую семантику. Реальный pen/touch ввод подтверждается на устройствах, а не только синтетикой Chromium.

### Обучающий режим

- Сверху или рядом с холстом — текущий шаг, цель, пример/референс и короткая подсказка; второстепенная теория не вытесняет область рисования.
- В панели инструменты: уже открытые, изучаемые сейчас и, при необходимости, недоступные с объяснением момента открытия.
- Режимы урока из утверждённой концепции — «Повтори», «Пойми», «Нарисуй сам» — используют одни проекты/команды; переключение не стирает работу без предупреждения.
- После завершения показывается понятный результат и следующий инструмент; доступен выход в свободную студию.

## 7. Устойчивость данных и совместимость

1. Сохранение остаётся локальным в IndexedDB, пока отдельно не утверждён сервер или синхронизация.
2. Учебный прогресс хранится отдельно от `DrawingProject`; удаление рисунка не удаляет факт изученного инструмента.
3. Любая миграция формата проекта имеет тесты «открыть → редактировать → Undo/Redo → сохранить → перезагрузить → экспортировать».
4. Удаление/редактирование слоя проверяется для масок, зависимостей, ссылочных ресурсов; при ошибке сохранения нет ложного статуса успеха.
5. Референсы и личные изображения не отправляются внешним сервисам без отдельного решения.
6. Существующий прототип v0.4 и незакрытые E1 PR не удаляются и не подменяются архитектурным изменением.

## 8. Дорожная карта и release gates

### R0 — Технический аудит (первый следующий этап после утверждения дизайна)

- Карта текущих зависимостей `EditorCanvas`, `model`, `render`, `events`, `history`, `useLocalProjects` и `Studio`.
- Реальные профили FPS/задержки ввода, памяти, времени сохранения и восстановления на фиксированных документах разной сложности.
- Матрица рисков формата v2, кэшей, поддержки stylus/touch и статуса E1 Draft.
- **Gate:** отчёт с воспроизводимыми командами и измерениями; обоснованный выбор минимального рефакторинга. Без кода профессиональных функций.

### R1 — Ядро доступа и два пространства (MVP архитектуры)

- Экспортируемый каталог реально работающих инструментов и чистая функция tool availability.
- Профессиональная оболочка с прежним полным набором; учебная оболочка с одним реальным коротким уроком.
- Постоянная разблокировка одного инструмента после завершения, сохранение прогресса и перенос проекта.
- **Gate:** unit-покрытие политик и миграций + E2E сценарий «урок → разблокировка → перезагрузка → следующий урок → свободная студия»; ни один действующий инструмент не исчез в Professional.

### R2 — Основа настоящего редактирования

- Выделение и трансформации как команды модели, история и сохранение без потери предыдущих рисунков.
- **Gate:** regression coverage undo/redo, старые проекты v2, экспорт и история; стресс-бенчмарки на измеренном оборудовании.

### R3 — Стилус, расширенные кисти и слои

- Pressure/tilt pipeline по реально поддерживаемым устройствам, маски/режимы наложения после миграций.
- **Gate:** автоматические тесты + обязательная приёмка реальным пером и большим документом; без реального устройства — **NOT TESTED**, не PASS.

### R4 — Профессиональный UX и учебная программа

- Настраиваемый интерфейс, сложные последовательные уроки, расширенное содержимое и переносимый формат.
- **Gate:** UX-проверки обоих режимов на desktop/tablet/phone, доступность и независимость прогресса от студии.

### Общие release gates

- Typecheck, unit, сборка, автоматические browser tests, визуальная приёмка; **критичные физические сценарии отдельно**.
- Нет merge/публикации в `main` по одному обещанию PASS без фактических артефактов.
- Каждый этап — самостоятельный небольшой PR, без «big-bang» переписывания всего редактора.
- Название «профессиональный» в маркетинговом интерфейсе используется после достижения согласованных возможностей и аппаратной приёмки, не автоматически после R1.

## 9. Решения для утверждения и остающиеся вопросы

### Подтверждённые

- Вариант A, обучение сохраняем, накопительное открытие инструментов, полный доступ в свободной студии, общий движок.

### Предложения автора, требующие утверждения дизайна целиком

- При выходе из урока в свободную студию делать явную редактируемую копию рисунка для защиты учебной попытки.
- Первый технический этап — R0 аудит; не начинать с переписывания рендера или интерфейса.
- Начать R1 с **одного** реального урока, а не сразу с полной учебной программы.
- Локальные разблокировки без регистрации и облачной синхронизации на первом этапе.

### Не определено и не блокирует R0

- Какой целевой диапазон устройств/размеров документов формально поддерживать; выбрать после измерений и физической проверки.
- Какие внешние редактируемые форматы действительно нужны помимо будущего собственного формата.
- Будут ли в дальнейшем аккаунты и синхронизация прогресса — отдельное решение.

**После утверждения:** составить подробный план **только R0**, пройти аудит и по его результатам согласовать объём R1. Этот документ не даёт разрешения на реализацию, merge или релиз.
