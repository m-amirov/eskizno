## 1. Краткий вывод

Текущее ядро можно сохранить как единственную основу для `Professional Workspace` и `Learning Workspace`: операции документа типизированы, сохраняемые объекты валидируются, локальное сохранение атомарно, рендер и экспорт используют один pipeline, а референс рядом с холстом уже имеет отдельный zoom/pan. Однако **готового профессионального ядра и учебного движка нет**: инструменты и их состояние связаны с UI `EditorCanvas`, давление стилуса не записывается, политики доступа к инструментам нет, учебная вкладка — стартовый экран. Безопасный следующий этап — ограниченный R1 с общим Tool Registry и централизованной Tool Policy; переработку рендера, pressure/tilt, маски и группы вынести в отдельные проверяемые этапы.

## 4. Риски по приоритету

### P0 — требуется решить **до** выпуска R1

1. **Политика инструментов сейчас не централизована.** Локальный `type Tool = 'ink'|'erase'|'fill'|'shape'|'eyedropper'` и `useState` находятся в `editor/EditorCanvas.tsx`; UI напрямую вызывает `onAction`, а `studio/useLocalProjects.ts` применяет `commitAction`. Простое скрытие кнопок в уроке не запретит выполнение запрещённой команды из другого пути. **R1:** Tool Registry с устойчивыми ID; Tool Policy для `professional` (все инструменты) и `learning` (постоянно накопленные unlocks + контекстный lesson allowlist); проверка на пути dispatch, а не только на отрисовке кнопок. Тест: запрещённая команда не меняет ни `history.present`, ни IndexedDB, ни прогресс.
2. **Нет готового учебного маршрута и модели unlocks.** `App.tsx` показывает заглушку; `ProgressState` хранит попытки и достижения, но не выданные инструменты. **R1:** один реальный урок, идемпотентная выдача инструмента после зафиксированного результата, постоянное восстановление unlocks после reload, возможность повторить урок без отъёма ранее открытых инструментов. Existing `ProgressState` v1 читать без потерь; миграцию прогресса покрыть тестами.
3. **Совместимость формата при расширении.** `parseDrawingProject` принимает **только v2** (`model.ts`), а сохранение `saveProject` повторно его валидирует; добавление новых структур в `Layer`/`Stroke` без стратегии миграции может скрыть старые работы из галереи (`listProjects` отбрасывает невалидное). **R1:** не повышать версию ради одного реестра инструментов; не вписывать UI unlocks в DrawingProject. Любая будущая v3 требует v2→v3 adapter, fixture round-trip и export parity.

### P1 — критично для профессиональной художественной функциональности, после R1 фундаментом

4. **У стилуса нет динамики мазка.** `Point = {x,y}`, `Stroke.points: Point[]` (`model.ts`), `pointerSamples` собирает только координаты (`EditorCanvas.tsx`); `brushes.ts` принимает фиксированную ширину штриха. `event.pressure`, `tiltX/tiltY`, twist и calibration не сохраняются. **Дальше:** расширение sample-контракта с fallback для старых документов и мыши, сохранение/replay, тесты чувствительности к давлению и hardware gate; нельзя объявлять «поддержку нажима» по PointerEvent API без реализации.
5. **Высокий memory ceiling.** Холст до **4096×4096** (`model.ts`) и до **16 слоёв**; каждый полноразмерный RGBA canvas требует минимум **64 MiB** только под пиксели, 16 одновременно ≈ **1 GiB**, без preview, истории и накладных расходов. `paintCache`/`shapePrefixCache` хранят поверхности по объектам слоёв, `renderProject` создаёт полноразмерную preview surface на активном слое. Это **расчёт верхнего порядка, не измеренный расход браузера**. **Дальше:** стенд 1024²/2048²/4096² × 1/8/16 слоёв, 100/1000/5000 операций, фиксировать peak RAM, latency pointermove и replay, время save/reload. Выбор tiling/dirty rect/worker — только по замерам.
6. **Заливка зависит от размера всего слоя.** `render.ts:paintBucketFill` делает `getImageData` на весь bitmap, выделяет `Int32Array(pixelCount)` и `Uint8Array(pixelCount)`, проходит очередь и `putImageData` всего слоя; при 4096² это дополнительно **80 MiB на queue+visited и 64 MiB на ImageData** (без canvas/других копий). Это расчёт объёма выделений, не замер peak RAM. **Дальше:** профиль memory/time, регрессии big closed area, отмена/повтор, эквивалентность PNG; избегать синхронного freeze UI.
7. **Концентрация ответственности в компоненте редактора.** `EditorCanvas.tsx` (~694 строк) управляет tool state, stroke gesture, shape edit, панелью, view и экспортом; `Studio.tsx` управляет загрузкой и ref layout. Добавление учебных ограничений туда напрямую усилит связанность. **Дальше:** вынести минимальные контрактные границы (registry/policy, dispatch, tools), не проводить одномоментную перепись JSX и рендера.

### P2 — планировать при развитии UX

8. **Undo и undo UX.** `history.ts` ограничивает историю 80 `DrawingProject`; свойства UI-инструментов (`brushId`, размер, выбранный цвет) вне документа. Изменения слоёв и опций могут давать отдельные команды; для сложных трансформаций понадобится транзакционное undo и отдельная история UI-настроек либо явно оговорённое поведение.
9. **Максимумы и форматы.** `MAX_LAYERS=16`, палитра до 32, экспорт только PNG, референсы PNG/JPEG/WebP до 10 MiB/16 Мп (`import-image.ts`). Это действующие продуктовые ограничения, а не дефекты; профессиональная спецификация должна определить, когда и как их расширять, прежде чем менять проверку сохранений.
10. **Экранная детализация и чувствительность к устройствам.** Canvas в JSX имеет buffer равный проекту; нет отдельной стратегии `devicePixelRatio` для всех режимов масштабирования. Для тонких линий и большого zoom оценить качество на Retina/Android/iPad, но не заявлять деградацию без сравнительных скриншотов.

## 5. Данные и миграции — обязательные сценарии

- **Старый v2:** открыть проект с `strokes` без `operations`, дорисовать, сохранить, reload, сравнить pixel output и количество операций; `model.ts:getPaintOperations` выполняет fallback. Затем проверить, что новые метаданные workspace не портят файл.
- **Старый v1:** текущий путь `persistence.ts:migrateLegacyV1` (уже покрыт модульным и E2E тестом); сохранить regression fixture и тест идемпотентности.
- **Reference asset:** `overlay`/`side` Blob сохраняется и восстанавливается с тем же ID, zoom боковой панели остаётся UI-only и не меняет экспорт или bitmap рисунка.
- **Save failure:** отказ IndexedDB/квота/вторая вкладка не показывает ложное `saved`; критические действия `New/Open/Delete` требуют успешного flush. Undo/redo после перезагрузки восстанавливает документ, но **не историю предыдущей сессии** (так работает текущая модель).
- **Future schema:** при v3 формат v2 конвертируется перед валидацией; несовместимая запись не должна молча исчезнуть из галереи.

## 6. R1 — минимальный вертикальный срез

1. **Registry (без UI изменений):** структурированная таблица `toolId`, название, capability, тип допустимых команд, default setting, metadata для progressive unlock. Все текущие 5 семейств инструментов и 10 кистей должны получить совместимые IDs; не менять сериализацию v2.
2. **Policy и dispatch:** `professional` раскрывает весь registry; `learning` вычисляет доступ через `earnedUnlocks ∩ lesson restrictions`, где ограничения урока временные, накопленные unlocks постоянные. Повторное событие выдачи не дублирует unlock. Запрет команды тестируется на границе Core.
3. **Один урок end-to-end:** старт/шаги/завершение, обязательный результат шага из accepted document event (см. `editor/events.ts`), выдача первого инструмента, save/reload; контрольный тест, что нельзя «пройти» урок кликом без рисования.
4. **Переход в свободную студию:** самостоятельная копия/продолжение работы без потери этюда и без переноса учебных запретов; UI сохраняет привычные имена инструментов и референс рядом.
5. **Regression:** fixture v1/v2, undo/redo, сохранение, JSON validation, 29 E2E в доступном CI, desktop/tablet/mobile viewport, keyboard reachability, `pointercancel`, pen+touch simulated. Реальный стилус отдельно; R1 можно считать software-gated, но не `hardware accepted`.

**Не включать в R1:** pressure/tilt, новый графический движок, bitmap masks, layer groups, selection transform, PSD, облачную синхронизацию, авторизацию или полный курс. Это отдельные этапы с метриками и совместимостью.

## 7. Решение по gate

- **GO на проектирование/реализацию ограниченного R1 после подтверждения заказчика:** общие Registry + Policy + один урок. Базовая архитектура позволяет инкрементальное развитие без немедленной замены Canvas2D.
- **NO-GO на публичное обещание «профессиональный редактор готов»:** давление пера не реализовано, уроки не реализованы, отсутствуют реальные измерения 2048²+/планшета, многослойная память не оценена.
- **NO-GO на release:** все соответствующие gates, включая реальные stylus/touch и performance на целевых устройствах, должны пройти фактически. Удалённый workflow #38 подтверждает только указанные программные проверки, а не hardware performance.

**Следующий запрос согласования:** разрешить R1 в новой изолированной feature-ветке с отдельным Draft PR и тестами. **Зависимость веток:** пока E1-7 живёт только в Draft PR #14 и отсутствует в `main`, R1 должен быть stacked поверх точного `feat/e1-7-finish` SHA; если E1-7 будет предварительно принят в `main`, начинать R1 уже от нового `main`. PR #14 и документационный PR #15 не сливать автоматически.
